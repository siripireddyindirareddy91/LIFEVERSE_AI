# 11. TECHNICAL ARCHITECTURE

Mobile application: - Flutter (stable channel) and Dart 3.x; select
mutually compatible stable versions and pin them. - Material 3 as a
foundation, with a fully custom LIFEVERSE design system; do not use an
unmodified Material template. - Riverpod for dependency injection and
state management. - GoRouter for declarative navigation, nested
navigation and deep links. - Dio for HTTP requests, interceptors,
cancellation, timeouts and refresh-token handling. - Freezed and
json_serializable for immutable typed models and JSON serialization. -
Flutter Secure Storage for sensitive local tokens; never store secrets
in ordinary preferences. - SharedPreferences only for non-sensitive
preferences. - Rive or Flutter's built-in animation system for the AI
orb and selected motion experiences; use Lottie only where it genuinely
fits. - CustomPainter and/or carefully selected Flutter rendering
primitives for radial navigation, constellation visuals and custom
charts. - Flutter Local Notifications and Firebase Cloud Messaging where
configured and permissioned. - Flutter localization (ARB files) with
English first and architecture ready for additional languages and RTL. -
Platform channels only when a required native capability is not
adequately supported by a maintained Flutter package. - Keep package
versions compatible with the installed Flutter SDK; avoid unnecessary
dependencies.

Flutter implementation requirements: - Create the mobile project in
`mobile/` using `flutter create` only after checking the installed
Flutter SDK and repository state. - Organize Flutter code by
feature/domain, not by a single oversized screens folder. Use a
structure such as `lib/app/`, `lib/core/`, `lib/shared/`, and
`lib/features/<feature>/` with each feature containing presentation,
application, domain and data layers where complexity justifies them. -
Establish design tokens for the supplied Aurora Nebula palette,
typography, spacing, radii, elevation, gradients, motion and semantic
colors. Support light and dark themes and accessible contrast. - Build
reusable components for buttons, fields, dialogs, bottom sheets,
navigation, charts, empty/loading/error states and approval previews. -
Implement the AI orb as a reusable animated Flutter widget with explicit
states: idle, listening, understanding, thinking, planning, executing,
awaiting approval, completed and error. Respect reduced-motion
settings. - Implement radial navigation with touch-friendly targets,
responsive fallbacks and an accessible conventional navigation path. Do
not make essential functionality depend on gestures alone. - Use
responsive layouts and test small phones, large phones and tablets.
Respect safe areas, keyboard insets, system text scaling and platform
navigation conventions. - Use semantic labels, focus order, keyboard
support where applicable, screen-reader support and sufficient
contrast. - Keep business logic out of widgets. Use Riverpod providers,
feature services and repositories; keep API DTOs separate from domain
models when useful. - Use Dio through a centralized API client with base
URL configuration, timeouts, typed errors, authentication interceptors
and safe token refresh. Never hardcode production endpoints or
secrets. - Generate and maintain model serialization consistently. Run
`dart format`, `flutter analyze` and relevant Flutter tests after
changes. - Use platform-specific code only when necessary and document
Android/iOS setup, permissions and limitations. - Do not assume iOS
builds can be produced on Windows; document that iOS signing and final
native builds require the appropriate Apple tooling and environment.

Backend: - Python. - FastAPI. - Pydantic. - SQLAlchemy. - Alembic. -
REST APIs. - WebSocket where needed.

AI: - LangGraph. - LangChain where useful. - LLM provider abstraction. -
RAG. - Embeddings. - Tool calling. - Structured output. - Agent
orchestration.

Data: - PostgreSQL. - Supabase Auth. - pgvector. - Redis. - Private
object storage.

Infrastructure: - Docker. - Background workers. - Cloud hosting. -
GitHub Actions. - Sentry. - OpenTelemetry. - PostHog.

Use a modular monolith first. Keep clear domain boundaries so services
can be separated later if necessary.
